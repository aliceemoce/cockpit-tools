# 禁止删除已有功能

## 用户纠正（权威）

### 2026-08-12 · NeeView 会话

- 你好像很喜欢删除功能
- 需要把禁止删除功能写在规则里

### 2026-08-14

- 总爱改一个程序的原本的功能，破坏原本功能来增加新功能
- 要在全局规则里禁止这么做

## 硬禁止

1. **修一个点不得砍其它能力**：改报错、改锁、改配置、改绑定、改性能时，禁止顺带删掉与本次修复**无关**的已有逻辑与能力。
2. **禁止为加新功能破坏原功能**：新需求落地时，禁止用「关掉/解绑/架空原能力」当实现手段；须保留原能力，或规格内等价替换且复验原能力仍在。
3. **禁止「简化版交差」**：不得把完整实现收成 stub / 最小可跑版，除非用户**当场**明确要求删减 scope。
4. **禁止静默缩功能**：删分支、删字段、删绑键、删验收/落盘路径 → 同条回复须逐条列出「删了什么、谁授权」；无授权 = 违规。
5. **禁止用「最小 diff」当借口删功能**：`Minimize scope` 只限**少加**无关新代码，不等于可以**少留**原有代码。

## 必须

1. **改前先读现盘全文**：列出改前能力清单；改后逐项对照，缺一项 = 未完工。
2. **修复 = 加法或等价替换**：例：文件锁 → `try/catch`、改写入时机、共享锁；**不得**用「去掉能力」代替「修好能力」，除非用户/规则已明确禁止该能力且已有等价替代。
3. **发现被删或变 stub**：同回合从 transcript / 备份 / 运行记录恢复，再叠加修复。
4. **用户只报一个症状**：只动因果链上的最小集合；其余功能保持行为不变。

## 违规 vs 正确

| 违规 | 正确 |
|---|---|
| 修锁 → 删掉写参、跳过、排序、dump | 保留全部能力；只修争用/报错点 |
| 「代码更干净」→ 删双写法兼容 | 兼容写法保留，除非实测证明无效且用户同意 |

## 与既有规则

- 同效加强：`no-compromise-half-done.mdc`、`no-distort-task-or-unasked-work.mdc`、`code-logic-same-as-language-order.mdc`
- 加新功能还须贴合宿主规格、禁止平行抢入口：`no-break-host-spec-for-new-features.mdc`
